# ОКО МЧС — бортовое компьютерное зрение (Рома, Vision Lead)

Статус: **готово к защите**. Ветка: `feature/vision-roma`.
Модуль не зависит от ROS в ядре и проверен двумя способами: офлайн на
синтетическом полигоне с наземной истиной и онлайн через реальные
ROS 2-топики (`/mchs/camera/image_raw`, `/mchs/odom`).

## 2. Поток обработки одного кадра

1. **Приём кадра** 640×480 BGR из ROS или файла.
2. **Перевод в HSV** и построение четырёх бинарных масок по порогам классов.
3. **Морфология**: `MORPH_OPEN` убирает одиночные пиксели, `MORPH_CLOSE`
   склеивает разрывы пятна (у дыма ядра больше, у огня меньше).
4. **Поиск контуров** и геометрические фильтры: минимальная площадь,
   заполненность bbox, соотношение сторон, касание краёв кадра.
5. **Текстурный фильтр**: СКО лапласиана внутри контура. Трава и листва
   «шумят», нефть/вода/дым — гладкие. Это главный способ отсечь ложные
   срабатывания на тёмную или серую растительность.
6. **Подавление перекрытий**: пиксели, уже занятые огнём, вычитаются из
   маски дыма; порядок приоритетов `FIRE → OIL_SPILL → FLOOD → SMOKE`.
7. **Склейка близких пятен** одного класса и выбор до 3 очагов на класс.
8. **Трекинг**: детекция подтверждается, если прожила `track_min_hits`
   кадров подряд; координаты и площадь сглаживаются EMA. Это убирает
   мерцание и одиночные выбросы.
9. **Геопривязка**: контур проецируется на плоскость земли, считается
   площадь, центр, дальность, пеленг и WGS-84.
10. **Классификация угрозы** по площади и **формирование события**.
11. **HUD** и публикация аннотированного кадра.

## 3. Классы ЧС и признаки

| Класс | Что ищем | HSV (OpenCV: H 0–179, S/V 0–255) | Мин. площадь |
|---|---|---|---|
| `FIRE` | яркое жёлто-оранжевое пламя | `H 5–25, S 120–255, V 180–255` | 250 px |
| `SMOKE` | светло-серый рассеянный дым | `H 0–180, S 0–45, V 160–230` | 700 px |
| `OIL_SPILL` | тёмное малосатурационное пятно | `H 0–180, S 0–75, V 15–65` | 400 px |
| `FLOOD` | сине-голубая вода | `H 95–125, S 80–255, V 60–200` | 600 px |

Почему такие признаки:

* **Огонь** — единственный объект с высокой насыщенностью и высокой
  яркостью одновременно в жёлто-оранжевом тоне. Трава и сухая листва
  обычно темнее (`V < 180`) либо менее насыщены.
* **Дым** — низкая насыщенность и средняя яркость. В надирной съёмке небо
  не попадает в кадр, поэтому главный конкурент — светлые крыши и пыль;
  их отсекают минимальная площадь и текстурный фильтр.
* **Нефть** — тёмное (`V 15–65`) и почти серое (`S < 75`) пятно. Тени от
  деревьев тоже тёмные, но у них высокая насыщенность зелёного и текстура,
  поэтому фильтр `S` + лапласиан их убирает.
* **Вода** — синий тон с высокой насыщенностью; на синтетическом полигоне
  стабильно `H ≈ 107`.

Пороги вынесены в `config.py` и могут быть переопределены без правки
алгоритма. Для реальной камеры их нужно калибровать по балансу белого и
освещённости (см. раздел 10).

## 4. Фильтрация, уверенность, трекинг

### Геометрические фильтры

* площадь контура не меньше `min_area_px` класса;
* площадь не больше 55% кадра (иначе это фон);
* заполненность bbox `area / (w*h) ≥ 0.10` — отсекает тонкие линии;
* соотношение сторон `max(w,h)/min(w,h) ≤ 10` — отсекает дороги и границы;
* контур не должен касаться 3+ краёв кадра — это фон, а не очаг.

### Текстурный фильтр

Для кадра считается `Laplacian(GaussianBlur(gray))`. Внутри контура
берётся СКО. Порог для нефти — 17, воды — 22, дыма — 26; для огня
текстурный фильтр отключён, потому что пламя само по себе неоднородно.
Гладкие пятна проходят, трава/кроны — нет.

### Уверенность

Эвристическая оценка 0…0.99:

```text
confidence = 0.30 * size_score      # площадь относительно минимума
           + 0.25 * fill_score      # заполненность bbox
           + 0.30 * color_purity    # «чистота» цвета класса
           + 0.15 * stability       # сколько кадров держится трек
```

`color_purity` для огня — насыщенность и яркость, для дыма — низкая
насыщенность, для нефти — близость к V≈40 и низкая S, для воды — близость
 Hue к 110 и высокая S. Итог обрезается снизу `min_confidence = 0.30`.

### Трекинг

Для каждого класса ведётся набор треков `TRK-<CLASS>-NNNN`. Детекция
сопоставляется с треком по IoU рамок или расстоянию между центрами.
Трек подтверждается после `track_min_hits` кадров (по умолчанию 2; в
офлайн-демо 1, чтобы работал одиночный кадр). Координаты и площадь
сглаживаются EMA с `alpha = 0.45`. Трек удаляется после
`track_max_missed = 5` пропусков.

## 5. Геопривязка: математика

### Системы координат

* Локальная СК: **X — восток, Y — север, Z — вверх** (ENU/ROS REP-103).
* `yaw = 0` — дрон смотрит на восток, положительный yaw — против часовой
  стрелки (к северу).
* Камера наклонена вниз на `pitch_down_deg`: `0°` — горизонт, `90°` — надир.
* Земля — плоскость `Z = 0`; рельеф не учитывается.

### Луч пикселя

Для пикселя `(u, v)`:

```text
x_n = (u - cx) / fx
y_n = (v - cy) / fy
fx = W / (2 * tan(FOV_x / 2))
fy = fx                     # квадратные пиксели
```

Орты камеры в СК корпуса (FLU: X вперёд, Y влево, Z вверх):

```text
f =  cos(p) * F - sin(p) * U     # куда смотрит камера
r = -L                            # вправо по кадру
d = -sin(p) * F - cos(p) * U     # вниз по кадру
```

Луч: `q = f + x_n * r + y_n * d`.
Пересечение с землёй: `t = -Z_cam / q_z`, точка `P = O + t * q`.

### Частный случай надира (формула из ТЗ)

При `p = 90°`:

```text
ΔX = (u - W/2) / W * Z * 2 * tan(FOV_x / 2)
ΔY = (v - H/2) / H * Z * 2 * tan(FOV_y / 2)
X_очага = X_дрона + ΔX
Y_очага = Y_дрона + ΔY
```

Важно: в ТЗ `ΔY` отсчитывается **вниз по кадру**. В нашей локальной СК
`Y` — север, поэтому в коде `d = -F` и знак `ΔY` противоположен.
Если в вашей системе `Y` направлен вниз/на юг, знак совпадёт с ТЗ.
На итоговые координаты это не влияет — важно лишь единообразие осей.

### Площадь

Контур проецируется по точкам на землю, площадь считается по формуле
шнуровки (`cv2.contourArea`) уже в метрах:

```text
S = |1/2 * Σ (x_i * y_{i+1} - x_{i+1} * y_i)|
```

Это корректно и для наклонной камеры: перспектива учитывается самим
проецированием, а не приближением «пиксели × GSD». Для надира результат
совпадает с `N_px * GSD_x * GSD_y`, где
`GSD = 2 * Z * tan(FOV_x/2) / W`.

### WGS-84

```text
lat = lat0 + Y / 111320
lon = lon0 + X / (111320 * cos(lat0))
```

`lat0/lon0` — точка привязки (по умолчанию Магнитогорск:
`53.4129, 58.9814`). Для RTK-точности эту формулу нужно заменить на
пересчёт ECEF/ENU, но для демонстрации хватает.

## 6. Уровни опасности

| Площадь очага | Уровень | Что значит |
|---|---|---|
| `< 15 м²` | `ADVISORY` | зафиксировать, наблюдать |
| `15…50 м²` | `WARNING` | доклад в ЦУКС, готовить наряд |
| `> 50 м²` | `CRITICAL` | немедленное реагирование |

Границы: ровно 15 м² — `WARNING`, ровно 50 м² — `WARNING`, больше 50 —
`CRITICAL`. Пороги задаются в `DetectorConfig` и могут быть изменены под
методику МЧС.

## 7. Контракт данных

### Топики

| Направление | Топик | Тип | Частота |
|---|---|---|---|
| подписка | `/mchs/camera/image_raw` | `sensor_msgs/Image` | 30 FPS |
| подписка | `/mchs/odom` | `nav_msgs/Odometry` | 20 Гц |
| публикация | `/mchs/detection_event` | `std_msgs/String` (JSON) | по событию/2–3 с |
| публикация | `/mchs/camera/annotated` | `sensor_msgs/Image` | каждый кадр |

### Пример JSON

```json
{
  "schema_version": "1.0",
  "event_id": "EVT-20261111-000001",
  "incident_id": "INC-2026-001",
  "timestamp": "2026-11-11T12:31:25+05:00",
  "frame": {"width": 640, "height": 480},
  "hazard_type": "FIRE",
  "hazard_label_ru": "Пожар",
  "threat_level": "CRITICAL",
  "area_sq_m": 57.09,
  "area_px": 5878,
  "confidence": 0.854,
  "track_id": "TRK-FIRE-0001",
  "target_geo": {
    "abs_x": 42.03,
    "abs_y": 98.37,
    "rel_x": 0.03,
    "rel_y": 0.37,
    "lat": 53.4137837,
    "lon": 58.9820335,
    "distance_m": 0.38,
    "bearing_deg": 5.2
  },
  "uav_pose": {"x": 42.0, "y": 98.0, "z": 38.14, "yaw_deg": 90.0},
  "detections": [
    {
      "hazard_type": "FIRE",
      "threat_level": "CRITICAL",
      "area_sq_m": 57.09,
      "confidence": 0.854,
      "bbox_px": {"x": 276, "y": 191, "width": 98, "height": 94},
      "target_geo": {"abs_x": 42.03, "abs_y": 98.37}
    }
  ]
}
```

Поля `abs_x/abs_y` — локальные метры (X восток, Y север), `lat/lon` —
WGS-84. `detections` содержит все подтверждённые очаги в кадре, а
верхнеуровневые поля дублируют главный (самый опасный) — так проще
потребителям, которые ждут один объект.

### Защита от флуда

`EventThrottle` пропускает событие, если инцидент новый, сменился уровень
опасности, площадь изменилась >25% или прошёл `cooldown_s` (3 с в ноде).
Жёсткий минимум между публикациями — `min_interval_s` (1 с в ноде,
2 с в демо).

## 8. Запуск

### 8.1. ROS 2-нода (Gazebo / реальный борт)

```bash
source /opt/ros/humble/setup.bash
python3 src/mchs_vision/scripts/mchs_vision_node.py
```

С параметрами из файла:

```bash
python3 src/mchs_vision/scripts/mchs_vision_node.py \
  --ros-args --params-file src/mchs_vision/config/vision_params.yaml
```

Окно OpenCV (WSLg):

```bash
python3 src/mchs_vision/scripts/mchs_vision_node.py \
  --ros-args -p show_window:=true
```

Важнейший параметр — `camera_pitch_down_deg`:

* `34.4` — текущая камера в `mchs_fire_zone.world` (наклон вниз);
* `90.0` — строго надирная камера (формула из ТЗ).

Если камера в модели изменится, поменяйте только этот параметр — формулы
пересчитаются.

### 8.2. Офлайн-демо на изображениях

```bash
python3 src/mchs_vision/scripts/make_test_scenes.py \
  --output /tmp/oko_mchs_dataset

python3 src/mchs_vision/scripts/vision_demo.py \
  --input /tmp/oko_mchs_dataset \
  --output /tmp/oko_mchs_demo \
  --json --csv
```

Результаты: `annotated/*.png`, `events.json`, `metrics.csv`,
`metrics.json`, `summary.json`. Временные файлы специально пишутся в
`/tmp`, а не в репозиторий. Из Windows те же файлы открываются по UNC-пути
`\\wsl.localhost\Ubuntu-22.04\tmp\oko_mchs_demo\`.

### 8.3. Видео полёта

```bash
python3 src/mchs_vision/scripts/make_demo_video.py \
  --output /tmp/oko_mchs_demo
```

На выходе `oko_mchs_vision_demo.mp4` (35.5 с, 960×720, 30 FPS),
`events.json`, `poster_demo.png`.

### 8.4. Полная проверка (pytest + демо + ROS)

```bash
bash src/mchs_vision/scripts/run_vision_tests.sh
```

Скрипт сам поднимает ноду, публикует синтетический кадр в реальные
топики и проверяет событие и аннотацию. Нужен ROS 2 Humble.

сцена, подтверждение трека, забывание трека, реестр инцидентов,
throttle событий, сквозной пайплайн и HUD.

### Производительность

На CPU WSL2 (Python 3.10, OpenCV 4.5.4) пайплайн 640×480 даёт
**35–45 FPS** (видно в HUD видео). ROS-событие формируется за доли
секунды после появления очага. На Jetson Orin Nano ожидается не хуже:
операции — HSV, морфология и контуры, без тяжёлой нейросети.

## 10. Интеграция с командой

1. **Камера в Gazebo наклонена, а не надирна.**
   В `mchs_fire_zone.world` у камеры `pose 0.15 0 0 0.6 0` — это
   ~34.4° вниз. Поэтому параметр ноды по умолчанию `34.4`, а не `90`.
   Геопривязка учитывает наклон честно; для надирной камеры поставьте
   `camera_pitch_down_deg:=90.0`. В ТЗ и презентации камера описана как
   надирная — стоит согласовать модель и текст.
2. **`odom.z` в Gazebo равен ~0.2 м.**
   `libgazebo_ros_planar_move` не поднимает дрон, поэтому нода использует
   `fallback_altitude_m=8.0`, если `z < min_valid_altitude_m=1.0`, и
   пишет предупреждение. Для корректной площади нужен плагин высоты
   (или чтобы Артём публиковал `odom.z = 8.0`). Иначе площадь будет
   считаться для высоты 8 м — это компромисс для демо.
3. **Топик события.**
   В главном `README.md` и старом коде упоминается `/mchs/fire_detected`,
   а по распределению ролей контракт — `/mchs/detection_event`. Моя нода
   публикует `/mchs/detection_event`. Артёму нужно подписаться на него
   (сейчас его автопилот летает по таймеру и событие не читает).
4. **АРМ оператора.**
   Соня может подписать `app.py` на `/mchs/camera/annotated` и
   `/mchs/detection_event`; сейчас её UI рисует синтетический кадр
   самостоятельно. Формат события описан в разделе 7.
5. **Класс «свалка/бочки».**
   В роли Руслана упоминается `waste_hazard`, но в моём ТЗ 4 класса:
   `FIRE, SMOKE, OIL_SPILL, FLOOD`. Архитектура расширяемая: добавьте
   `HazardClassSpec` в `config.py` с HSV-диапазоном мусора/бочек — и
   детектор подхватит его без правки пайплайна.
6. **Смещение камеры.**
   В `CameraConfig` учтено смещение `mount_forward_m=0.15`, `mount_up_m=-0.05`.
   Если Руслан изменит посадку камеры, эти значения нужно обновить.

## 11. Ограничения и что улучшать

* **HSV зависит от освещения и баланса белого.** На синтетике пороги
  идеальны; на реальных фото нужна калибровка. Для жюри это честно
  проговаривается: классика объяснима, но чувствительна к свету.
* **Дым и облака/светлые крыши** могут давать ложные срабатывания.
  Помогают текстурный фильтр, минимальная площадь и подтверждение
  трека, но 100% гарантии нет.
* **Ночь и тепловизор** не поддержаны: HSV работает по RGB. Для LWIR
  нужен отдельный канал (нормализация яркости, порог по температуре).
* **Плоская земля.** На склонах, крышах и мостах площадь и координаты
  будут смещены; для точности нужен DEM или фотограмметрия.
* **Дисторсия объектива** не учитывается: в Gazebo камера идеальная,
  реальную нужно калибровать (`cv2.calibrateCamera`).
* **Пострадавшие** не детектируются: в ТЗ это пример, а не обязательный
  класс; для людей нужна нейросеть (YOLO), HSV их не найдёт надёжно.
* **Трекинг** теряет объект после 5 пропусков; при длительном перекрытии
  дроном/деревом очаг получит новый `track_id`.
* **WGS-84** — плоское приближение; для RTK-точности нужен пересчёт
  ECEF/ENU и привязка к геодезической системе.

**Дорожная карта:**

1. Собрать 200–500 реальных аэрофотоснимков пожаров/разливов/воды,
   откалибровать HSV и добавить лёгкую YOLOv8n/ONNX-модель на Jetson.
2. Добавить тепловизионный канал (FLIR Boson) и fusion RGB+LWIR.
3. Учитывать рельеф (DEM) и дисторсию камеры.
4. Перевести пакет в colcon-пакет с `setup.py` и launch-файлом.
5. Добавить класс `WASTE` (свалка/бочки) и детектор пострадавших.

## 12. Для презентации (Соня)

Краткая шпаргалка — в `VISION_FOR_SLIDES.md`: 5 тезисов на слайд 5,
формулы, цифры и ответы на вероятные вопросы жюри.

Три главных числа:

* **4 класса ЧС** — огонь, дым, нефть, затопление;
* **0.12 м** — средняя ошибка координат на тестовом полигоне;
* **7.5%** — средняя ошибка площади, **100%** совпадение уровней угрозы.

## 13. Git

Работа ведётся в ветке `feature/vision-roma`, `main` не трогается.
Коммиты:

1. `feat(vision): core detection/geometry/events/HUD package`
2. `feat(vision): ROS 2 node, offline demo, synthetic dataset, tests`
3. `docs(vision): algorithm, formulas, results and integration notes`

Перед вливанием:

```bash
git checkout feature/vision-roma
git status
bash src/mchs_vision/scripts/run_vision_tests.sh
```

Затем Pull Request в `main` на ревью Руслану.
