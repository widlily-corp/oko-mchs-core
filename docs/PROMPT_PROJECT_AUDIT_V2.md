# Промпт v2.0 — аудит и доведение «ОКО МЧС» до боевого качества

**Версия:** 2.0 от 12.11.2026  
**Зачем:** v1 был слишком «чек-листовым» — сильная модель могла имитировать проверку галочек. v2 устроен как охота на дефекты: гипотезы, доказательства, фиксы с регрессией и честный отчёт.  
**Куда вставлять:** агентный инструмент с доступом к терминалу WSL (Claude Code, Codex CLI, Cursor Agent, Windsurf, OpenHands, DSH).

---

## 0. Как пользоваться

1. Откройте проект в агентном инструменте, который умеет запускать команды в WSL.
2. Проверьте доступ:
   ```bash
   wsl.exe -d Ubuntu-22.04 -- bash -lc "cd /root/oko-mchs-core && python3 --version && source /opt/ros/humble/setup.bash && ros2 --version"
   ```
3. Вставьте промпт целиком одним сообщением. Режим по умолчанию — `FIX_SAFE`; для первого прогона можно поставить `AUDIT_ONLY`.
4. Запретите агенту `git push`, `git reset --hard`, `git clean`, удаление веток/тегов и всё необратимое.
5. После работы проверьте: `git log --oneline`, `git diff`, полный pytest, отчёт в `docs/audit/`.

> Веб-чат без доступа к терминалу не сможет провести честный аудит: он увидит только приложенные файлы. Для исправлений нужен агентный режим.

## 1. КОНТРАКТ РЕЗУЛЬТАТА

Работа закончена только когда:
1. Полный pytest: 0 failed/error, passed не меньше baseline, 3 прогона стабильны.
2. `python3 -m compileall -q src scripts tests` — чисто.
3. Нет открытых P0/P1; P2 либо исправлены, либо внесены в отчёт с обоснованием.
4. На каждый исправленный баг есть regression-тест или документированное ручное воспроизведение.
5. Публичные контракты не изменены; если изменены — есть обратная совместимость, миграция и тест.
6. Demo smoke пройден: синтаксис `run_all.sh`, генератор мира, `estimate_fire_area.py`, `diagnose_logs.py`, headless-импорты, UI `--offline` (если доступен Windows).
7. Документация синхронизирована с кодом.
8. `git status` содержит только намеренные изменения; артефакты не в индексе.
9. Отчёт заполнен и воспроизводим: команды, выводы, «до/после».

Это бинарные критерии, а не пожелания. Если что-то не выполнено — пиши это в отчёте, не имитируй выполнение.

## 2. ПРАВИЛА ИГРЫ

1. Evidence or it didn't happen. Три уровня доказательств:
   - E1 — исполнено: команда + вывод/лог/тест.
   - E2 — прочитано и прослежено: путь вызова, file:line, объяснение.
   - E3 — гипотеза: подозрение без проверки.
   E3 нельзя выдавать за факт и нельзя «чинить» как доказанный баг. В отчёте уровень указывается у каждой находки.
2. Сначала прочитай — потом меняй. Проследи потребителей: кто вызывает функцию, кто читает файл, кто зависит от формата.
3. WIP неприкосновенен. Если дерево грязное — сохрани `git diff` и `git status` в /tmp, не откатывай чужие изменения. Если чистое — всё равно проверь `git log`: возможно, работа уже частично сделана.
4. Не меняй публичные контракты без необходимости: ROS-топики, поля JSON-событий/протокола, схему hazards.json/mission.json, CLI-флаги, имена файлов отчётов. Если изменение неизбежно — обратная совместимость, миграция, тест.
5. Никаких новых тяжёлых зависимостей, нейросетей, облачных API и сетевых вызовов в рантайме. Офлайн — жёсткое требование. Python 3.10: не используй синтаксис/API из 3.11+.
6. Минимальные диффы. Один логический фикс — один коммит. Не смешивай рефакторинг с поведением. Никаких массовых переформатирований и смены line endings. Не коммить секреты, логи, отчёты и бинарники; используй `git add -p`, а не `git add .`.
7. Тесты — закон. Баг сначала воспроизводится падающим тестом, потом исправляется. Не отключай тесты (`skip`, `xfail`, удаление) и не подгоняй их под баг, чтобы получить зелёный прогон.
8. Документация — свидетель, а не истина. README и docs могут врать; проверяй код и запускай команды. Каждое расхождение — находка.
9. Дисциплина скоупа: не переписывай то, что не относится к находке. Не «оптимизируй» без профилирования. Не меняй архитектуру ради архитектуры.
10. Никаких необратимых команд: `git reset --hard`, `git clean -fdx`, `git push --force`, удаление веток/тегов, `rm -rf` без разрешения. Работай в локальной ветке `audit/ai-fixes-<YYYYMMDD>`, не push, main не переключай.
11. Честность важнее красоты отчёта. Непроверенное — в раздел «не проверено». Не выдавай «кажется» за «доказано». Если нашёл 0 багов — покажи, что именно и как пытался опровергнуть.
12. Архитектурные развилки — не героизм, а согласование. Если фикс требует изменения контракта или более 3 файлов — остановись, опиши варианты и риски.

## 3. КАРТА ПРОЕКТА

«ОКО МЧС» — хакатонный комплекс мониторинга ЧС с БПЛА: ROS 2 Humble + Gazebo 11 + OpenCV + АРМ на CustomTkinter. Репозиторий: `/root/oko-mchs-core` (WSL Ubuntu 22.04). Из Windows: `\\wsl.localhost\Ubuntu-22.04\root\oko-mchs-core`.

Подсистемы:
- `src/mchs_simulation` — мир Gazebo 11 (арена 200×200 м), SDF-модели (`largedrone`, `person_standing`), генератор мира из `config/hazards.json`, `arena_controller.py` (перемещение очагов через gz service), launch.
- `src/mchs_vision` — детектор ЧС на классическом CV (HSV → морфология → контуры → геометрия/текстура → трекинг), геометрия (`GroundProjector`, WGS-84), площадь пожара (`fire_area`), события/инциденты/троттлинг, HTTP-стрим `:8080` (MJPEG, `/snapshot.jpg`, `/state.json`), ROS-нода.
- `src/mchs_control` — автопилот: полный FSM (`mchs_pilot_node.py`) и демо-сканер (`mchs_pilot_route.py`), генератор отчётов.
- `src/mchs_ui` — АРМ оператора на CustomTkinter (Windows): карта, камера/тепловизор, телеметрия, протокол, видеоотчёт, перетаскивание очагов.
- `src/mchs_core` — логирование (`logs/`, `events.jsonl`, crash handler), чёрный ящик телеметрии (20 Гц), видеорапорт. Не ROS-пакет, импортируется через PYTHONPATH.
- `config/` — `hazards.json` (единый источник координат), `mission.json` (план полёта, арена, топики).
- `tests/` и `src/*/tests|test` — pytest-тесты, идут без ROS и GUI.
- `scripts/` — `run_all.sh`, утилиты (`estimate_fire_area.py`, `diagnose_logs.py`).

Поток данных:
Gazebo camera → `/mchs/camera/image_raw` → vision-нода → детекции/события
  → `/mchs/detection_event` (JSON) → автопилот (инспекция/RTL) и АРМ (протокол)
  → аннотированный кадр → HTTP `:8080` → АРМ (видео, `/state.json`)
  → `reports/`: `incident_protocol.json`, `incidents/*.jpg`, `video/*.mp4`, `mission.cmd`
`config/hazards.json` → генератор мира, `arena_controller.py`, карта АРМ, сопоставление в зрении.

Инварианты, которые нельзя ломать:
- Офлайн; Gazebo не тянет модели из Fuel; нет облачных API.
- Соответствие ТЗ кейса (`docs/task.md`): обнаружение, классификация, геопозиционирование, передача данных, автономность. Аудит не должен «оптимизировать» эти требования в сторону.
- Без тяжёлых нейросетей: классический CV, CPU-бюджет (Jetson Orin Nano), объяснимость для жюри.
- Камера 1280×720, HFOV 80°, наклон 45°, высота 22 м — значения обязаны совпадать в `model.sdf`, `vision_params.yaml`, `config.py`, `mission.json`.
- `hazards.json` — single source of truth координат; запись атомарная; неизвестные поля не теряются.
- Русскоязычный UI/доки; отчёты с кириллицей; WGS-84.
- Запуск демо: `run_all.bat` → `scripts/run_all.sh` → Gazebo + vision + pilot + АРМ.
- Публичные контракты: топики, поля JSON, схемы конфигов, CLI-флаги, имена файлов отчётов.

Окружение и baseline:
```

PYTHONPATH=src:src/mchs_vision:src/mchs_core:src/mchs_control:src/mchs_ui:scripts \

```

## 5. КЛАССЫ ОТКАЗОВ (глубокая проверка)

Помимо гипотез, пройди по классам. Вопросы — не для галочек, а для поиска конкретных дефектов.

### A. Корректность
- Что будет при None/NaN/Inf/0/пустом входе на каждом публичном entrypoint?
- Где единицы перепутаны (px/m/deg/ha/WGS-84), знак угла неверен, lat/lon переставлены?
- Где данные из JSON/файла попадают в расчёты без валидации?
- Где округление, порядок аргументов или границы массива дают неверный результат?
- Какие инварианты обязаны выполняться и где они не проверяются?

### B. Конкурентность
- Кто пишет/читает общие файлы, state, frame, protocol?
- Какие блокировки есть, в каком порядке берутся, что будет при shutdown в середине операции?
- Где daemon-потоки и что будет при выходе/повторном запуске?
- Где возможен deadlock, потеря события или чтение частичного файла?

### C. Ресурсы
- Где растут очереди/списки/файлы без ограничения?
- Что утекает: сокеты, файлы, VideoWriter, окна OpenCV, subprocess, потоки?
- Что будет при длительном полёте (часы), переполнении диска, отсутствии прав?
- Где таймауты внешних вызовов отсутствуют?

### D. Интеграция и среда
- Что будет, если Gazebo/vision/UI упали или перезапустились?
- Как ведёт себя WSL↔Windows: пути, UNC, кириллица, пробелы, DPI, отсутствие python в PATH?
- Совпадают ли FOV/pitch/разрешение/высота в SDF, YAML, Python, JSON?
- Что будет без интернета, без дисплея, при занятом порту 8080?

### E. Безопасность
- HTTP `0.0.0.0`: кто может подключиться, что видит, можно ли выйти за пределы?
- subprocess: без shell, списки аргументов, таймауты, валидация путей/команд?
- Файлы: symlink, UNC, tmp, TOCTOU, запись вне разрешённых каталогов?
- Секреты/токены/IP в коде и логах?

### F. Тесты
- Покрыты ли критические пути: FSM, геометрия, дедуп, троттлинг, shutdown, ошибки?
- Детерминированы ли тесты: tmp_path, seed, нет сети/дисплея/времени/Gazebo?
- Не пишут ли тесты в реальные `config/`, `reports/`, `logs/`?
- Флакуют ли performance-тесты? Есть ли маркеры slow/integration?
- Не «подогнаны» ли тесты под текущее поведение?

### G. Документация и репозиторий
- Каждая команда из README/docs реально выполняется?
- Числа, координаты, структура, имена модулей совпадают с кодом?
- Нет ли tracked-артефактов, бинарников, логов?
- Есть ли `.gitattributes`, CI, LICENSE; нужны ли они проекту?

### H. Архитектура и сопровождаемость
- Где дублирование логики/констант, которое уже разошлось?
- Где монолит мешает тестировать и провоцирует регрессии?
- Где `sys.path`-хаки и неявные зависимости от cwd?

## 6. ПРИОРИТЕТЫ

- P0: падения при старте/демо, потеря или порча данных, дыры в безопасности, неверные координаты/площадь, блокеры приёмки, регрессии.
- P1: гонки, утечки, потеря событий, ошибки FSM/RTL, флаки, опасные пути, неверные единицы.

- P3: стиль, косметика, «nice to have».

Порядок: P0 → P1 → P2 (если MODE) → P3 в отчёт. Не начинай с косметики.

## 11. СТОП-ПРАВИЛА
