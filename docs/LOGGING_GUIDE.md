# Руководство по архитектуре логирования комплекса «Око МЧС»

Настоящее руководство описывает архитектуру логирования, форматы данных, методику расследования инцидентов и работу с утилитой экспресс-диагностики `scripts/diagnose_logs.py` для беспилотного комплекса мониторинга чрезвычайных ситуаций «Око МЧС».

---

## 1. Архитектура и принципы подсистемы логирования

Подсистема логирования комплекса решает три критические задачи:
1. **Оперативный контроль (Real-Time Observability):** цветовая консоль оператора и АРМ ЦУКС для мгновенного обнаружения нештатных ситуаций.
2. **Машиночитаемый аудит (Machine-Readable Auditing):** структурированный поток событий JSONL для интеграции с внешними системами и аналитики.
3. **Расследование летных происшествий (BlackBox Telemetry & Crash Dumps):** высокочастотная некольцуемая телеметрия и посмертные дампы памяти при авариях.

```
+-------------------------------------------------------------------------------+
|                             ИСТОЧНИКИ ДАННЫХ                                  |
|   mchs_pilot_node        mchs_vision_node           АРМ Оператора (GCS_UI)    |
|   (Автопилот / Навигация) (Детекция ЧС / Камера)    (CustomTkinter Windows UI)|
+-----------------------------------+-------------------------------------------+
                                    |
                    +---------------+---------------+
                    |     mchs_core.get_logger      |
                    |     mchs_core.log_event       |
                    |  mchs_core.BlackBoxRecorder   |
                    +---------------+---------------+
                                    |
+-----------------------------------v-------------------------------------------+
|                          СТРУКТУРА КАТАЛОГА logs/                             |
|                                                                               |
|  logs/                                                                        |
|  |-- system.log               <- Единый вращающийся лог (10 МБ x 5 файлов)   |
|  |-- pilot.log                <- Лог подсистемы навигации и автопилота        |
|  |-- vision.log               <- Лог компьютерного зрения и детекции ЧС       |
|  |-- gcs_ui.log               <- Лог АРМ Оператора (действия, кнопки, UI)     |
|  |-- events.jsonl             <- Структурированные события (JSON Lines)       |
|  |-- telemetry_blackbox.csv   <- Черный ящик БПЛА (20-50 Гц)                  |
|  `-- crashes/                 <- Посмертные дампы падений (Crash Dumps)       |
|      `-- crash_<node>_<timestamp>.log                                         |
+-------------------------------------------------------------------------------+
```

## 2. Структура каталога `logs/` и спецификация форматов

### 2.1. Текстовые системные логи (`system.log`, `<subsystem>.log`)

Используется стандартный вращающийся логгер (`RotatingFileHandler`, лимит 10 МБ, 5 копий ротации).

**Формат строки:**
```
[YYYY-MM-DD HH:MM:SS.mmm] [SUBSYSTEM] [LEVEL] Message
```
- `YYYY-MM-DD HH:MM:SS.mmm` — метка локального времени с миллисекундами.
- `SUBSYSTEM` — идентификатор подсистемы (`CORE`, `PILOT`, `VISION`, `GCS_UI`, `SIM`).
- `LEVEL` — стандартные уровни Python logging (`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`).
- `Message` — текстовое описание события или форматированный трассировочный блок исключения.

### 2.2. Машиночитаемый журнал событий (`events.jsonl`)

Каждая строка представляет собой валидный JSON-объект, сериализованный в кодировке UTF-8:
```json
{
  "timestamp": "2026-11-11T14:15:30.124Z",
  "epoch_s": 1794406530.124,
  "subsystem": "GCS_UI",
  "event_type": "OPERATOR_ACTION",
  "level": "INFO",
  "data": {
    "action": "SELECT_HAZARD",
    "sector": "ПОЖАР",
    "hazard_key": "FIRE",
    "title": "ОЧАГ ЛЕСНОГО ПОЖАРА",
    "threat": "CRITICAL"
  }
}
```

**Ключевые типы событий (`event_type`):**
- `OPERATOR_ACTION` — действия оператора в АРМ (взлет, RTL, смена сектора, экспорт протокола).
- `HAZARD_DETECTED` — фиксация компьютером зрения одного из 4 типов ЧС (Пожар, Нефть, Паводок, Свалка).
- `FSM_STATE_CHANGE` — переход конечного автомата автопилота (`IDLE` -> `TAKEOFF` -> `PATROL` -> `INSPECT` -> `RTL` -> `LANDED`).
- `NAV_ALERT` — предупреждения навигационного контура (просадка GPS HDOP, расхождение EKF).
- `STREAM_CONNECTED` / `STREAM_ERROR` — статус связи с видеостримером бортовой камеры (:8080).

### 2.3. Полетный черный ящик (`telemetry_blackbox.csv`)

Высокочастотная запись кинематики, ориентации и состояния энергоустановки БПЛА. Запись ведется в отдельном фоновом потоке через кольцевой буфер очереди, не блокируя контур управления полетом.

**Заголовок CSV:**
```csv
timestamp,epoch_s,x,y,z,yaw_deg,vx,vy,vz,battery_pct,state,hazard_alert,message
```

**Описание полей:**
| Поле | Тип | Единицы | Описание |
|------|-----|---------|----------|
| `timestamp` | string | ISO 8601 UTC | Штамп времени кадра телеметрии |
| `epoch_s` | float | секунды | Unix Epoch с точностью до 0.1 мс |
| `x`, `y`, `z` | float | метры | Координаты БПЛА в локальной системе ENU (полигон 50×50 м) |
| `yaw_deg` | float | градусы | Курсовой угол рыскания (0–360°) |
| `vx`, `vy`, `vz` | float | м/с | Линейные скорости в локальном базисе |
| `battery_pct` | float | % (0–100) | Текущий уровень заряда тяговой АКБ |
| `state` | string | ENUM | Состояние FSM автопилота |
| `hazard_alert` | bool | True / False | Флаг активной тревоги по обнаруженной ЧС |
| `message` | string | текст | Служебное сообщение автопилота / навигации |

### 2.4. Каталог аварийных краш-дампов (`crashes/`)

При возникновении необработанного исключения в любом из потоков (`sys.excepthook`), обработчик `install_crash_handler("<SUBSYSTEM>")` формирует атомарный файл:
`logs/crashes/crash_<subsystem>_<YYYYMMDD_HHMMSS>.log`

Файл содержит:
- Полный traceback с номерами строк и именами исходных файлов.
- Системную информацию (ОС, версия Python, архитектура).
- Снимок локальных переменных последнего стекового фрейма (Local Variables Dump).

## 3. Автономная утилита диагностики: `scripts/diagnose_logs.py`

Утилита предназначена для мгновенной оценки состояния комплекса, локализации ошибок, восстановления хронологии аварии и формирования пакета техподдержки.

### 3.1. Сводный статус здоровья системы (`--summary`)

Выполняется по умолчанию при запуске без параметров:
```powershell
python scripts/diagnose_logs.py
# или явно:
python scripts/diagnose_logs.py --summary
```
**Пример вывода:**
```
================================================================================
 🏥 СВОДНЫЙ СТАТУС ЗДОРОВЬЯ КОМПЛЕКСА «ОКО МЧС»
================================================================================
Статус комплекса:        🟢 [OK] ВСЕ СИСТЕМЫ В НОРМЕ
Каталог логов:           6 файлов (245.8 КБ)
Аварийных дампов (crash): 0
Критических инцидентов:   0
Ошибок (ERROR):           0
Предупреждений (WARN):    2
Черный ящик:             ДОСТУПЕН (1420 строк, АКБ: 91.2%)
--------------------------------------------------------------------------------
```

### 3.2. Аудит ошибок и сбоев (`--errors`)

Сканирует все файлы `.log`, `events.jsonl` и папку `crashes/`.
```powershell
python scripts/diagnose_logs.py --errors
```
> [!IMPORTANT]
> Если найдены аварийные дампы в `crashes/` или строки с уровнем `CRITICAL`, утилита завершается с **exit code 1**. Это позволяет использовать ее в CI/CD пайплайнах и автоматических чек-скриптах сдачи этапа.

### 3.3. Объединенная хронологическая лента (`--timeline`)

Склеивает и синхронизирует по таймстемпам текстовые логи, события `events.jsonl` и ключевые точки черного ящика:
```powershell
# За всю сессию
python scripts/diagnose_logs.py --timeline

# За последние 5 минут
python scripts/diagnose_logs.py --timeline --minutes 5
```

### 3.4. Анализ черного ящика БПЛА (`--blackbox`)

Рассчитывает ключевые летно-технические характеристики полета:
```powershell
python scripts/diagnose_logs.py --blackbox
# или с указанием произвольного CSV-файла:
python scripts/diagnose_logs.py --blackbox --csv path/to/blackbox.csv
```
**Выводимые параметры:**
- Длительность полета (мин, сек).
- Пройденная дистанция (3D интеграция трека).
- Максимальная высота и пиковая скорость.
- Расход батареи и темп разряда (%/мин).
- Процент времени в каждом режиме FSM (IDLE, TAKEOFF, PATROL, INSPECT, RTL).
- Количество зарегистрированных алертов ЧС.

### 3.5. Сборка диагностического пакета (`--bundle`)

Создает единый zip-архив инцидента, включающий все логи, краш-дампы, отчеты и манифест:
```powershell
python scripts/diagnose_logs.py --bundle
```
Архив сохраняется в `reports/incident_bundle_<YYYYMMDD_HHMMSS>.zip`.

## 4. Инструкция по расследованию типовых инцидентов

### Сценарий 1: Падение ноды (Node Crash / Exit 1)
1. Запустите: `python scripts/diagnose_logs.py --errors`.
2. Если в блоке `АВАРИЙНЫЕ КРАШ-ДАМПЫ` есть запись:
   - Откройте указанный файл `logs/crashes/crash_<node>_*.log`.
   - Изучите строку `Traceback (most recent call last):` и блок `Local variables:`.
   - Найдите значение переменной, вызвавшей сбой (например, `NoneType`, деление на 0 или потеря дескриптора сокета).

### Сценарий 2: Потеря видеопотока бортовой камеры (:8080)
1. В АРМ Оператора статус связи отображается бейджем камеры и в журнале ЦУКС.
2. Проверьте `gcs_ui.log` и `events.jsonl`:
   ```powershell
   python scripts/diagnose_logs.py --timeline --minutes 3
   ```
3. Ищите события `STREAM_DISCONNECTED`. Если ошибка `urllib.error.URLError: Connection refused`:
   - Видеостример ноды компьютерного зрения или мост Gazebo не запущены.
   - Проверьте доступность порта: `netstat -ano | findstr 8080`.

### Сценарий 3: Зависание симулятора / Срыв RTF (Real-Time Factor)
1. Выполните: `python scripts/diagnose_logs.py --blackbox`.
2. Обратите внимание на дельту `epoch_s` между соседними строками:
   - Если дельта `epoch_s` превышает 0.2 с при штатной частоте 20 Гц (0.05 с) — контур физики Gazebo перегружен.
   - Проверьте загрузку CPU/GPU процессом `gzserver`.

### Сценарий 4: Дрейф БПЛА / Ошибка одометрии
1. Постройте таймлайн событий навигации:
   `python scripts/diagnose_logs.py --timeline`
2. Найдите события `NAV_WARN` или резкие скачки координат `x`, `y`, `z` в отчете `--blackbox`.
3. Сверьте расчетную скорость `max_speed_ms`. При скачке > 30 м/с имел место скачок фильтра EKF.

## 5. Интеграция в АРМ Оператора (Windows UI)

В графическом интерфейсе АРМ Оператора (`src/mchs_ui/app.py`):
1. **Автоматическое журналирование:** Любое действие оператора (нажатие кнопки «Аварийный возврат (RTL)», переключение режима тепловизора, выбор очага ЧС, генерация протокола) автоматически дублируется в:
   - Локальный виджет журнала оперативного дежурного.
   - Файл `logs/system.log` через `logger.info(...)`.
   - Структурированный поток `logs/events.jsonl` через `log_event("GCS_UI", "OPERATOR_ACTION", ...)`.
2. **Кнопка «📦 ДИАГНОСТИЧЕСКИЙ ПАКЕТ»:** Расположена на нижней командной панели. При нажатии:
   - Вызывает функцию `build_diagnostic_bundle()`.
   - Атомарно архивирует все активные логи и протоколы в `reports/incident_bundle_<YYYYMMDD_HHMMSS>.zip`.
   - Выводит статус формирования в журнал оператора с указанием имени файла.
